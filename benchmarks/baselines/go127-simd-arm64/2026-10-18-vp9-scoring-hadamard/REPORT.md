# VP9 BlockYrd scoring transform — short native screen

Parent bc5e178048d18bdb2ea7801b7830a1e1f24ad0f6; candidate-hadamard is isolated from the ML cache. Six source/test files in hadamard.patch, exact hashes in hadamard-source.json. The independent native baseline transform shim is parent/internal/vp9/encoder/hadamard_score_baseline_test.go; it calls unchanged parent production Hadamard dispatch. The public BlockYrd benchmarks require no shim.

Reference: pinned libvpx 1.16.0 1024874c5919305883187e2953de8fcb4c3d7fa6, vpx_dsp/arm/hadamard_neon.c vpx_hadamard_8x8_neon/16x16_neon; vp9/encoder/vp9_pickmode.c block_yrd. C omits the second 8×8 transpose for scoring. Go previously computed canonical coefficient layout, materialized each butterfly/transpose through a stack matrix, recursively re-entered feature dispatch four times for 16×16, and widened that combine to 32-bit lanes.

The private BlockYrd-only transform leaves DC fixed and transposes AC positions within each 64-coefficient quadrant, retaining identical values. Quantization has uniform AC parameters; BlockYrd consumes only all-zero, DC-only vs other-nonzero, SATD and squared error, all invariant to that shared permutation. Canonical Hadamard helpers and their full signed-int16 contract remain unchanged. BlockYrd differences are in [-255,255], giving 8×8 coefficients within ±16320; each pre-halving sum is within ±32640, so the 16×16 combine needs only eight signed16 lanes. Input/output windows are validated before exact 16-byte pointer loads/stores; BlockYrd places residual and coefficient slabs in disjoint regions.

Correctness: 800 scalar-layout/permutation cases (two sizes, four strides, 100 patterns including ±255 extremes), 300 full BlockYrd scalar-consumer cases (known/unknown SSE, zero/DC/dense, quantizer extremes), existing Hadamard/BlockYrd tests, race+checkptr all pass. 72 public packets across 64×64, 320×180 and 352×288 match length-delimited parent SHA256. Logs: hadamard-targeted.log, hadamard-race.log, hadamard-*-stream.log. No coding-decision or numerical tolerance change.

LLVM evidence: hadamard-{parent,candidate}-llvm.txt from actual measured ARM binaries. New 8×8 leaf has no calls or stack frame, eight input vector loads and eight output stores, one 24-shuffle transpose. Parent hadamardGo has a 240-byte frame; its 8×8 path calls two butterflies and two transposes. Those helpers plus the caller materialize 40 intermediate vector loads and 40 stores per 8×8. The second transpose adds another 24 shuffles. These are instruction/dataflow observations, not a general cycle model.

Apple M4 Max / Darwin arm64 / Go1.27.2 archsimd / CGO1 / PGOoff / GOMAXPROCS1.
